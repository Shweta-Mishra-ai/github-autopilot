# Full audit — September 2026

Companion to the [reliability audit](reliability-audit.md) (*is it safe today?*)
and the [roadmap](roadmap.md) (*what next?*). This one answers a blunter
question: **can this project succeed, and what stands between it and that?**

Every claim below is evidence-backed or marked as unverified. Where something
could not be checked from the audit environment, it says so rather than
guessing.

---

## 1. Can it succeed?

**Not as a hosted PR-review SaaS. Yes as the self-hosted, agent-native one —
and the second is already most of what is built.**

### What the market actually looks like

Measured on GitHub at the time of writing:

| | |
|---|---|
| Repositories under `topic:ai-code-review` | 715 |
| This repository | 23 stars · 5 forks · 7 months old |

The leaders in that topic, and what they lead with:

| Project | Stars | Age | Wedge |
|---|---:|---|---|
| `hyhmrright/brooks-lint` | 1,471 | ~6 mo | Claude Code / Codex / Gemini **plugin**, not a service |
| `HexmosTech/git-lrc` | 1,463 | ~7 mo | Runs on **git commit**, local, free |
| `kodustech/kodus-ai` | 1,371 | ~18 mo | **Full control over model choice and cost** |
| `duriantaco/skylos` | 789 | ~16 mo | **Local-first** pre-merge scanner |

Two patterns, and neither is "a hosted bot that comments on pull requests":

1. **Agent-harness native.** The fastest riser is a plugin for the coding
   agents developers already run. It has no server at all.
2. **Local-first and cost-transparent.** Three of the four lead on the code or
   the money staying under the user's control.

Head-on, the hosted-bot lane is the one lane that cannot be won from here. It
contains CodeRabbit, Greptile, Qodo and GitHub's own Copilot code review —
funded teams, all free for open source. Competing there means competing on
review quality against companies whose entire payroll is review quality, while
also paying for inference.

### Why the other two lanes are winnable — and already half-built

The assets that matter are in the tree today:

- **`LLM_LOCAL_ONLY=1`** — Ollama or nothing, fail-closed, with no setting that
  weakens it. Nothing a private or regulated repository can use has to leave
  the building. `kodus-ai` reached 1,371 stars on a weaker version of this
  claim.
- **An MCP server and a Claude Code plugin**, both shipped. That is the lane
  `brooks-lint` is winning, entered already.
- **A real eval suite** (`evals/`) running nightly against planted bugs, with a
  pass-rate gate and an issue opened on regression. Almost nobody in that list
  of 715 can say what their review quality is, let alone that it is measured.
- **Engineering rigor that reads as trustworthy**: 2,286 tests, 85% coverage,
  bandit and pip-audit in CI, and generated documentation that fails the build
  when it drifts.

The honest verdict: **the product is good and the positioning is wrong.** The
README's first line sells PR review — the one thing that is commodity. The
privacy mode is halfway down the page, and the MCP/plugin story is below that.

> **Note on scope.** "Can it succeed on Amazon" is read here as commercial
> viability generally. Nothing in this project is shaped like an Amazon
> listing. If AWS Marketplace was meant specifically, that is a different
> exercise — it needs a container listing, an AMI or SaaS metering integration,
> and a seller account — and it should not be attempted before the positioning
> below is settled.

### What to change, in order

1. **Lead with the wedge.** Rewrite the top of the README around *"AI code
   review that never sends your code anywhere"* and *"works inside the agent
   you already use."* PR review becomes a feature of that, not the headline.
2. **Make the private path the quickstart.** Right now the 10-minute
   quickstart requires a Groq key, which means shipping code to a third party.
   There should be an equally short Ollama path.
3. **Publish the eval numbers.** A number nobody else in the category can
   quote is the strongest credibility asset here, and it is currently a
   workflow that files issues rather than a claim on the front page.
4. **Push the plugin, not the deployment.** `/plugin install` is a
   ten-second adoption path. A GitHub App plus a Render deploy plus five
   environment variables is not.

## 2. What was verified working

Run in this audit, not taken from documentation:

| Check | Result |
|---|---|
| Full test suite (`-m "not e2e and not integration"`) | **2,289 passed** |
| Coverage | **85%** (floor is 80%) |
| `ruff check` + `ruff format --check` on `app/` | clean |
| `bandit` (medium severity / medium confidence) | **no issues identified** |
| Command registry vs. dispatcher | **27/27 wired**, none silently unhandled |
| Import cycles | none |
| Unreferenced modules | none |
| CI on `main` | green — 9 jobs run, release skipped (tag-only) |
| Nightly evals | running and passing |
| Keep-alive ping of production | passing |

**The features are not broken.** Every slash command in the registry has a
dispatcher branch, every AI output path goes through `guarded_ask()`, and every
failure path returns a written explanation rather than silence — `fmt_error`,
`degraded_comment`, `providers_down_comment` and `command_disabled_comment`
between them cover provider outage, unparseable model output, low confidence,
permission refusal, and operator-disabled commands. That last point is worth
stating plainly because it was raised as a concern: **the bot already writes
the professional explanation when something fails.** Nobody has to hand-write
one.

One hole in that guarantee was found and closed — see the empty-response guard
below. No path through the comment handler now ends without a reply.

### What could not be verified

The live deployment at `github-autopilot-1.onrender.com` was **unreachable from
the audit environment** — the network proxy refused the host (HTTP 403 on
CONNECT), and the configured MCP server failed to connect for the same reason.
So nothing here is a statement about production behaviour. The indirect
evidence is that the scheduled keep-alive workflow has been green continuously,
which means production answers `/ping`.

To check production directly, from a machine with network access:

```bash
BASE_URL=https://github-autopilot-1.onrender.com METRICS_AUTH_TOKEN=... \
  ./scripts/verify-deployment.sh owner/repo <installation_id>
```

That is the only thing that can catch the failure class a green test suite
cannot: a model id the provider has retired, which took every AI command down
for six days once already.

## 3. What was actually broken — and is now fixed

### The graph was invisible, and two bugs made it look broken

Seeing the codebase map required a running deployment **and**
`METRICS_AUTH_TOKEN` **and** JavaScript. Three preconditions between a reader
and the only diagram in this project derived from code rather than drawn by
hand. In practice nobody saw it.

On top of the gating, two real defects, both reproduced in a browser:

1. **The page opened a native `prompt()` before its first request.** With
   `METRICS_AUTH_TOKEN` unset, `/graph.json` is open — and the page still
   demanded a secret that does not exist. With it set, the modal gave no
   context and no way to correct a typo; dismissing it stored an empty string,
   the fetch returned 401, and the page rendered "Unauthorized".
2. **The canvas height subtracted a fixed header height.** The header wraps
   when narrow, so on a 390px screen the canvas overflowed the viewport by
   44px (measured). There was also **no touch handling at all** — mouse events
   only — so on a phone the map drew and then ignored every gesture, with the
   sidebar hidden below 820px.

Fixed in three parts:

- `app/intelligence/graph_svg.py` renders the same data as a **committed SVG**
  with no script, no fetch and no auth, embedded in the README. A reader on the
  GitHub project page now sees the real structure at that commit. It is
  byte-reproducible so CI can diff it.
- The page asks for a token **only after a request has been refused**, through
  an in-page form, and every failure state links to the SVG instead of
  dead-ending on a status code.
- Pointer events with pinch-to-zoom, a flex column layout, and a render loop
  that stops when the layout settles instead of redrawing a static picture at
  60fps forever.

### A dead file was shadowing a live module

`app/handlers/comments.py` and `app/handlers/comments/__init__.py` both
resolved to the import path `app.handlers.comments`. Python always prefers the
package, so the `.py` shim could never be imported — including by itself; its
one statement would have been a self-import.

It was not merely dead. `codegraph` keys nodes by import path, so the second
file scanned overwrote the first. Path ordering put the shim last, so the map
described a 12-line file that cannot run while the 106-line package that
dispatches all 27 commands was **absent from the picture entirely**. 94 Python
files produced 93 nodes and nothing said so.

Fixed: the shim is deleted, `add_module()` records collisions instead of
overwriting, and CI fails on `stats.collisions` alongside cycles and orphans.

### One command outcome answered with silence

`handle_comment_event()` ended with `if not response: return` on a log line.
That branch is reached only *after* the comment carried a real command, the
author was permitted to run it, and the command was enabled — so somebody is
waiting for an answer, and got nothing.

Silence there is the worst available answer, because it is indistinguishable
from the deployment being down, the webhook never arriving, and the command not
existing. All three send the reader somewhere useless. (Silence is right
elsewhere in this codebase: a re-pushed PR with a clean review says nothing,
because nobody asked it a question. Here somebody did.)

No dispatcher arm currently returns empty — that is now asserted directly by
parsing the `match` statement — so this is a safety net rather than a live bug.
It is the structural guarantee that the concern raised about silent features
cannot become true later.

### Smaller

- `scripts/verify.sh` now warns when the local ruff differs from the pinned
  version. The formatter changes between releases, so a newer local ruff
  reports files CI considers clean — and "fixing" them makes CI reject them.

## 4. Gaps, ranked

Nothing below is currently failing. These are the things that will bite.

### High — adoption, not correctness

1. **Positioning.** Section 1. This is the single highest-leverage change in
   the repository and it is a writing task, not an engineering one.
2. **No hosted demo anyone can try.** Evaluating this costs a GitHub App, a
   Render deploy and five environment variables. Every competitor above is one
   command. The Claude Code plugin is the closest thing to a zero-cost trial
   and it is not promoted.
3. **Single maintainer, 20k lines.** 5 forks and 2 open issues. The bus factor
   is 1, and the codebase is now large enough that a second contributor needs
   `CONTRIBUTING.md` to be genuinely sufficient. It is good; it has not been
   tested by a stranger.

### Medium — will bite under real load

4. **`--workers 1` is load-bearing and undocumented outside comments.** The
   thread pool and router are process-wide singletons. Anyone who raises the
   worker count to handle traffic gets duplicated queue consumers and split
   rate-limit state. This deserves a boot-time check, not a comment.
5. **The 15-day maintenance sweep runs on a daemon thread on free-tier
   infrastructure that restarts often.** The due time is in Redis so a restart
   cannot reset the clock, and `/health` reports `overdue` — but nothing acts
   on `overdue`. A schedule that has silently stopped looks exactly like one
   that is running.
6. **Zero integration tests.** CI says so explicitly: there are no tests marked
   `integration`, and the Redis service was removed from the matrix because
   nothing connected to it. The queue, idempotency and rate limiting are all
   tested against an in-process fake. Their real failure modes — eviction,
   connection loss mid-transaction, cluster failover — are untested.
7. **No load test.** Bounds are chosen and enforced (queue 200, envelope 512KB,
   dead-letter 50) but never measured. Nobody knows what webhook rate a free
   Render instance sustains before returning 503.

### Low — worth doing, not urgent

8. **`docs/` has drifted.** `docs/diagrams/diagrams.md` still describes "26
   slash commands" and a `comments.py` monolith that no longer exists. The
   README is gated against drift; the rest of `docs/` is not.
9. **Coverage floor is 80% and actual is 85%**, but the gap is concentrated in
   the provider adapters — the code that talks to the services most likely to
   change under the project's feet.
10. **`app/intelligence/embeddings.py` and the Qdrant path** are optional and
    lightly exercised. If that is not a real feature, removing it is one less
    thing to maintain.

## 5. Security posture

Strong, and stronger than the category norm. Verified this pass: bandit clean
at medium/medium, pip-audit in CI, fail-closed webhook and MCP auth,
constant-time comparisons, path allowlist plus prefix blocklist plus traversal
guard on autofix, prompt-injection sanitisation with delimiter escaping,
oversized bodies refused during read rather than after, and no
`eval`/`exec`/`subprocess`/`pickle` anywhere in `app/`.

Two things to keep honest:

- **`TRUSTED_PROXY_HOPS` is silently wrong in both directions.** The doctor
  compares it against observed forwarding chains, which is the right design —
  but only if someone runs the doctor. Consider a warning on `/health` when the
  observed chain length disagrees with the configured value.
- **Config is read from the default branch, never a PR head.** This is correct
  and deliberate. It is also the kind of decision a well-meaning contributor
  "fixes". It deserves a test that fails loudly, not only a comment.

## 6. The 90-day plan

**Weeks 1–2 — positioning.** Rewrite the README top around privacy and
agent-native use. Add an Ollama quickstart equal in length to the Groq one.
Put the eval pass-rate on the front page. No code required.

**Weeks 3–4 — make trying it free.** Promote the Claude Code plugin to the
primary install path. A ten-second install with no server is the only funnel
that competes with the leaders above.

**Weeks 5–8 — close the medium gaps.** A boot-time check that refuses more than
one worker process. Integration tests against a real Redis in their own CI job.
A load test that produces a number for "webhooks per minute on free tier".

**Weeks 9–12 — earn the second contributor.** Fix the stale `docs/`, label
genuine good-first-issues, and answer the one open proposal. A project with a
bus factor of 1 and 20,000 lines is a project most people will not adopt,
regardless of how good it is.

## What "reliable, stable, trustworthy" honestly means here

**Reliable** — yes, for what it is tested against. 2,286 tests, no cycles, no
dead code, fail-closed security, and honest degradation on every AI path. The
untested surface is the infrastructure boundary: Redis under real failure, and
the providers when they change their catalogue.

**Stable** — yes in CI, unproven under load. The bounds exist and are enforced;
none has been measured.

**Trustworthy** — this is its strongest claim, and the most under-sold. The bot
discloses which model wrote every comment, refuses to publish a review it is
not confident in rather than fabricating one, measures its own quality nightly,
and regenerates its own documentation so the numbers cannot be stale. Very
little in this category can say any of that.

The gap between this project and success is not engineering. It is that almost
nobody knows the above is true, because the front page sells the one thing
everyone else is also selling.
